Cross-Site Request Forgery — How Browsers Are Turned Against Their Users

CSRF abuses something fundamental about how browsers work: they automatically attach cookies to every request, regardless of where the request originated. This post explains the mechanics behind that trust, the conditions that make an application exploitable, the two most common attack vectors, and the defences that reliably stop them.

The Vulnerability

What Is Cross-Site Request Forgery?

Modern web applications remember who you are through session cookies. When you log in, the server issues a cookie that your browser stores and automatically sends with every subsequent request to that domain. It is a seamless mechanism — and it is exactly what CSRF exploits.

Cross-Site Request Forgery is an attack where the victim is tricked into triggering an authenticated request they never intended to make. A malicious page on a completely different domain causes the victim's browser to fire a request at a site where the victim is already logged in. Because the browser dutifully attaches the session cookie, the target application sees a perfectly legitimate-looking request — and acts on it.

The attack does not steal credentials. It does not break into the account. It simply hijacks the trust the application already has in the victim's authenticated session, using the victim's own browser as the delivery mechanism.

CSRF in one sentence: The attacker does not need to know your password — they just need to make your browser ask the server to do something while you are already logged in.

Mechanics

How the Attack Works

To understand CSRF, you first have to understand that browsers are not broken — they are behaving exactly as designed. The problem is not with the browser; it is with web applications that place too much trust in requests that arrive with a valid session cookie.

Here is the sequence that makes a CSRF attack possible:

  1. The victim logs in to a legitimate web application. The server creates a session and sets a cookie in the victim's browser.
  2. Without logging out, the victim browses to a malicious page — perhaps through a phishing link, a forum post, or an embedded image in an email.
  3. That malicious page contains a request targeting the legitimate application: a hidden form, an image tag with a crafted URL, or a small JavaScript snippet.
  4. The victim's browser sends the request. Because the request is going to the legitimate domain, the browser automatically attaches the session cookie.
  5. The legitimate application receives a request with a valid session cookie and processes it as if the user had initiated it themselves.

The critical insight is that the browser does not distinguish between a request initiated by the user clicking a button and a request triggered silently by a malicious page. Both carry the same cookie. The application cannot tell the difference either — unless it was specifically built to check.

What Kind of Actions Are Affected?

CSRF targets state-changing requests — actions that modify data rather than simply read it. Typical examples include:

  • Changing an account email address or password
  • Updating profile information or security preferences
  • Submitting forms that perform transactions or purchases
  • Adding, removing, or modifying records in an application
  • Escalating user privileges or changing role assignments

Read-only requests — a GET that just fetches a page — are rarely worth targeting, because the attacker cannot see the response anyway. The damage from CSRF comes from actions, not data retrieval.

Prerequisites

The Three Conditions for a Successful CSRF Attack

Not every endpoint is exploitable via CSRF. Three conditions must align for an attack to succeed. Understanding them tells you both where to look when testing and what a developer needs to break to prevent exploitation.

ConditionWhy It Matters
Victim is authenticated The attack depends entirely on a valid session cookie being present. If the user is not logged in, the forged request carries no meaningful authority.
Action is state-changing CSRF only has value when the triggered request actually does something — changes data, submits a form, modifies account settings. Read-only endpoints are not useful targets.
Request origin is not verified If the application checks that requests originated from its own pages — via a CSRF token, the Origin header, or the SameSite cookie attribute — a forged request will be rejected before it causes any damage.

GET vs POST — A Common Misconception

Developers sometimes assume that switching a sensitive action from a GET request to a POST request provides CSRF protection. It does not. A malicious page can trigger a POST request just as easily as a GET — using a hidden HTML form that auto-submits with JavaScript. The HTTP method is irrelevant; what matters is whether the application verifies the origin of the request.

That said, GET requests deserve special scrutiny. Because they can be triggered by something as simple as an <img> tag or a URL in an email, any state-changing action that responds to a GET request is particularly easy to abuse — no form submission required.

Exploitation

Common Attack Vectors

The payload delivery mechanism depends on what the vulnerable endpoint accepts. The attacker's goal is always the same — get the victim's browser to fire the request — but the technique varies by request type and application behaviour.

Hidden Auto-Submitting Form (POST)

The most versatile CSRF payload is a hidden HTML form that submits itself automatically when the page loads. Because the form targets a different domain, the browser includes that domain's session cookie when it submits. The victim sees nothing — the request is sent and the page may redirect away in under a second.

Malicious page — hidden auto-submitting form
<html>
<body>

<form action="https://target.com/update_email.php"
      method="POST"
      id="attack">
  <input type="hidden" name="email" value="attacker@evil.com">
</form>

<script>
  document.getElementById("attack").submit();
</script>

</body>
</html>

The moment an authenticated victim opens this page, their browser submits the form — changing their email address to the attacker's value, without the victim clicking anything. The application sees a valid session cookie and processes the request normally.

Image Tag (GET)

If the vulnerable action accepts a GET request, the attack shrinks to a single HTML tag. An <img> with a src pointing at the target URL is enough — browsers fetch image sources automatically, cookie and all, with no user interaction required.

GET-based CSRF via img tag
<img src="https://target.com/delete_account?confirm=true" width="0" height="0">

This can be embedded anywhere user-generated content is rendered — a forum post, a support ticket, a product review. The request fires for every visitor who views the page and happens to be logged in to the target site.

Event-Triggered Requests

A subtler variation uses JavaScript event handlers to delay the request until the victim interacts with the page — hovering over an image, clicking a banner, or scrolling past a certain point. This can be used to bypass basic bot detection or to make the attack feel more like a legitimate redirect.

Mouseover-triggered GET request
<img
  src="https://target.com/banner.png"
  onmouseover="window.location='https://target.com/update_role?role=staff&csrf_token=YWRtaW4='"
  width="400">

The page appears to show a legitimate company banner. When the victim moves their mouse over it, the browser is redirected to the vulnerable URL — carrying the session cookie and a forged CSRF token the attacker pre-calculated.

Hidden Auto-Submit Form
Triggers instantly on page load. Works against any POST endpoint with no additional user interaction required.
GET
Image / Link Tag
The simplest payload. A single tag embedded in any page or email silently fires the request for every authenticated visitor.

Bypassing Defences

Weak CSRF Tokens — A False Sense of Security

CSRF tokens are the standard defence: a secret, per-session value embedded in every sensitive form. When the form is submitted, the server verifies the token matches what it issued. Since the malicious page on a different origin cannot read the token from the legitimate site's DOM, it cannot forge a request that will pass validation.

That protection only holds if the token is actually unpredictable. A token that is derived from something the attacker already knows — or can easily guess — is no protection at all.

Predictable Token Generation

A common mistake is generating the CSRF token from deterministic user data — the username, user ID, or role — then encoding it with a reversible transform like Base64. The result looks opaque but is trivially reversible:

Weak token embedded in a form
<input type="hidden" name="csrf_token" value="YWRtaW4=">

Decode YWRtaW4= from Base64 and you get admin — the user's role, plainly encoded. The developer added a CSRF field and believed the application was protected. In reality, any attacker who knows the target's role (often inferrable from the application's behaviour) can generate the correct token themselves and forge the entire request.

This pattern appears more often than it should. The lesson is not that CSRF tokens are a bad idea — they are the correct defence — but that the security of the token depends entirely on its unpredictability. A token generated from HMAC(session_id, secret_key) with a server-side secret is sound. A token generated from base64(username) is not a token at all; it is decoration.

Red flag during testing: If a CSRF token looks like it might be encoded rather than random — check for Base64, hex, or a recognisable pattern — always attempt to decode and reverse it. A surprising number of real-world applications will fail this check.

Defence Layer

How to Stop CSRF

CSRF is well understood and reliably preventable. The defences below are listed in order of effectiveness — most applications should implement several layers, not just one.

CSRF Tokens — Done Properly

The correct implementation of a CSRF token is a cryptographically random value, unique per session (or ideally per request), stored server-side and embedded in every state-changing form. On submission, the server compares the submitted token to the stored one and rejects any mismatch.

The token must be truly random — generated by a cryptographically secure source, not derived from user data. It must travel through the request body or a custom header, not a cookie (otherwise it provides no additional protection over the session cookie itself).

SameSite Cookie Attribute

The SameSite attribute on a session cookie controls when the browser includes it in cross-site requests. Setting it to Strict or Lax dramatically reduces the attack surface:

ValueBehaviour
Strict The cookie is never sent with cross-site requests. Provides the strongest protection but may break legitimate cross-site navigation (e.g. following a link from an email).
Lax The cookie is sent on top-level navigations (clicking a link) but not on cross-site form submissions or resource loads like images. Balances security and usability — the modern browser default.
None The cookie is always sent with cross-site requests. Requires Secure. Offers no CSRF protection and should only be used for explicitly cross-site functionality.

SameSite=Lax is now the default in most major browsers, which has meaningfully reduced the CSRF exposure of applications that never thought about it. But it is not a complete defence on its own — certain top-level GET navigations can still carry the cookie under Lax.

Origin and Referer Header Validation

Modern browsers include an Origin header on cross-origin requests, specifying the domain the request came from. Checking this server-side is a simple, effective secondary control: if the Origin does not match your own domain, reject the request. The Referer header provides similar information but is slightly less reliable (some browsers omit it for privacy reasons). Neither should be the primary defence, but both are useful supplementary checks.

Requiring Re-Authentication for Sensitive Actions

For the most critical actions — changing a password, updating an email, approving a large transaction — requiring the user to re-enter their password provides a layer of protection that CSRF fundamentally cannot bypass. Even if the forged request carries a valid session cookie, the attacker does not know the victim's password and cannot supply it.

  • Generate CSRF tokens using a cryptographically secure random source. Never derive them from user attributes or encode predictable data.
  • Validate the token server-side on every state-changing request. Reject anything that does not match, including requests with missing tokens.
  • Set the SameSite attribute to Lax or Strict on all session cookies. This alone blocks the most common CSRF patterns in modern browsers.
  • Validate the Origin or Referer header as a secondary check for sensitive endpoints.
  • Never implement state-changing actions on GET endpoints — this makes them trivially exploitable via image tags and embedded links.
  • Require re-authentication for high-impact account changes such as email, password, or payment details.

The bottom line: Proper CSRF tokens combined with SameSite=Lax cookies eliminate the vast majority of CSRF risk. Adding Origin header validation and re-authentication for critical actions makes an application genuinely robust. The weakness to watch for is not in the defence concept — it is in the token implementation. A token that is predictable or re-usable is worse than no token, because it gives developers false confidence while leaving users exposed.
