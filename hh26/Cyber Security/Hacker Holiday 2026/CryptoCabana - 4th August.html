CryptoCabana - 4th August

This room focuses on exploiting misconfigured Azure Storage and Azure Key Vault permissions.

The scenario begins with an exposed Azure Storage SAS (Shared Access Signature) token. Using that token, we enumerate storage containers, retrieve sensitive files, authenticate as an Azure Service Principal, and finally access Azure Key Vault to recover secrets—including an older version of a rotated secret.

What is a SAS Token?

A Shared Access Signature (SAS) is a signed URL token that grants temporary access to Azure Storage resources without exposing the storage account key.

The permissions contained inside the token determine what actions are allowed.

In this room the token allowed:

  • Read
  • List

Although these permissions appear limited, they were sufficient to access sensitive data.

Why Service Principal?

A Service Principal is a non-human identity used by applications and automation.

Unlike normal users, it authenticates using:

  • Client ID
  • Client Secret
  • Tenant ID

Successful authentication means we now inherit whatever Azure permissions were assigned to that identity.

Step 12 – Investigating Secret Versions

The room hint mentions that something looked different "five minutes before."

Azure Key Vault automatically versions secrets whenever they are updated.

This successfully revealed the older secret value.

The room demonstrates that rotating a secret does not destroy previous versions unless they are explicitly removed or purged. Any identity with permission to access secret versions can still retrieve historical values.

Security Issues Identified

1. Exposed SAS Token

The storage account exposed a SAS token that granted read and list permissions.

Impact

  • Container enumeration
  • File enumeration
  • Sensitive file download

2. Sensitive Credentials Stored in Blob Storage

The storage container contained:

  • Wallet seed phrase
  • Azure Service Principal credentials

Both should never be publicly accessible.

3. Over-Privileged Service Principal

The service account had permission to access Azure Key Vault secrets.

This violated the principle of least privilege.

4. Secret Version Exposure

Old versions of secrets remained accessible.

Even after rotating a secret, previous versions continued to expose sensitive information.

Key Takeaways

  • SAS tokens must follow the principle of least privilege and expire quickly.
  • Sensitive credentials should never be stored in publicly accessible storage accounts.
  • Service Principals should have only the permissions required for their specific tasks.
  • Azure Key Vault secret rotation should be accompanied by proper management or removal of outdated secret versions when appropriate.
  • Cloud security assessments should always include checks for exposed storage resources, over-permissive identities, and recoverable historical secrets, as these can enable privilege escalation even without compromising a user account.

Remediation

  • Use least-privilege SAS tokens with only the minimum required permissions (avoid unnecessary List and Read access).
  • Set short expiration times for SAS tokens and rotate them regularly.
  • Never store credentials, seed phrases, or secrets in publicly accessible Azure Blob Storage.
  • Store sensitive information only in Azure Key Vault with strict access controls.
  • Apply the Principle of Least Privilege (PoLP) to Service Principals by granting only the permissions they require.
  • Restrict Azure Key Vault access using Azure RBAC and managed identities where possible.
  • Regularly audit and remove old secret versions that are no longer needed.
  • Enable Azure Monitor and Key Vault logging to detect unauthorized access attempts.
  • Periodically review Storage Account and Key Vault permissions for misconfigurations.
  • Rotate compromised credentials immediately if exposure is detected.

Conclusion

This room demonstrates how a seemingly low-risk exposure—an Azure Storage SAS token with read/list permissions—can cascade into a full compromise of sensitive cloud resources. By enumerating Blob Storage, downloading exposed service principal credentials, authenticating to Azure, and abusing overly permissive Key Vault access, an attacker can retrieve both current and historical secrets. The exercise reinforces the importance of least-privilege access, secure credential storage, short-lived SAS tokens, and proper management of Azure Key Vault secret versions as core cloud security best practices.
