Beach Bar - 31st July

Objective

The objective of this challenge was to gain initial access to the target machine by identifying a vulnerable feature in the web application and then perform privilege escalation to obtain both the user and root flags.

Initial Enumeration

The challenge hint suggested that the vulnerability was related to "something exposed on either source code or somewhere else."

Another hint stated that:

"Song queue accepts more than song titles."

This indicated that the application might be processing user input rather than treating it as plain text. It suggested the possibility of injecting malicious payloads.

A second hint mentioned:

"Night-shift developers wired the jukebox straight into the floor with trimming attached."

This implied that developers may have left sensitive information inside the application, such as credentials, comments, configuration files, or hidden functionality.

Based on these hints, the first step was to inspect the website.

Step 1 - Inspecting the Source Code

After opening the target web application, the page source was inspected.

Inside the HTML source code, login credentials were found commented out by the developers.

Credentials discovered

  • Username: dj
  • Password: dj

These credentials allowed successful authentication into the application.

Step 2 – Identifying the Vulnerable Functionality

After logging in, the navigation menu contained an Import page.

The import feature accepted either:

  • .yml files
  • YAML snippets

YAML is commonly used for configuration files and data serialization. However, when Python applications use PyYAML with an unsafe loader, YAML can contain Python-specific tags capable of constructing Python objects during deserialization.

One such tag is:

!!python/object/apply
!!python/object/apply

This is not standard YAML. It is understood only by PyYAML when unsafe deserialization is enabled.

Before attempting exploitation, it was necessary to verify whether the application processed Python YAML tags.

The following payload was submitted:

playlist:
  name: !!python/tuple [Sunset, Session]
  vibe: golden hour
  tracks:
    - artist: Khruangbin
      title: Maria Tambien
playlist:
  name: !!python/tuple [Sunset, Session]
  vibe: golden hour
  tracks:
    - artist: Khruangbin
      title: Maria Tambien

The application successfully interpreted the Python-specific tag and returned the expected output.

This confirmed that the application was using unsafe PyYAML deserialization.

Understanding the Payload

Normally, YAML only stores data.

Example:

name: Vasu
age: 21
name: Vasu
age: 21

However,

!!python/object/apply:subprocess.check_output
!!python/object/apply:subprocess.check_output

instructs PyYAML to invoke the Python function subprocess.check_output() while parsing the YAML document.

The supplied arguments become the parameters passed to the function.

Conceptually, the deserialization behaves similarly to:

subprocess.check_output(
    ["id"],
    text=True
)
subprocess.check_output(
    ["id"],
    text=True
)

The command executed successfully and returned the output of the id command, including:

  • UID
  • GID
  • Groups

This confirmed that arbitrary operating system commands could be executed through the vulnerable YAML parser.

Step 4 – Obtaining a Reverse Shell

Since arbitrary command execution was confirmed, remote shell access could be established.

First, a Netcat listener was started on the attacking machine.

The vulnerable application was then supplied with a YAML payload that launched a shell process.

After the payload was processed, the target initiated a connection back to the listener, providing an interactive shell.

Step 6 – Enumerating Running Processes

The next step was local enumeration.

Running:

ps aux
ps aux

revealed a process executing as the root user.

The command line of this process contained the argument:

--stream-pass SunsetSpritz2024!

Initially, it was unclear what this value represented.

Since the process was owned by root, it was reasonable to suspect that the exposed value might be a password used by the privileged account.

Step 7 – Privilege Escalation

The discovered password was tested against the root account.

Using:

This completed the privilege escalation phase.

Vulnerability Summary

Initial Access

The application used unsafe PyYAML deserialization to process user-supplied YAML files. By abusing Python-specific YAML tags, arbitrary system commands could be executed, resulting in Remote Code Execution (RCE) and a reverse shell.

Privilege Escalation

A root-owned process exposed sensitive credentials through its command-line arguments. The exposed password was reused to authenticate as the root user, leading to full system compromise.

Attack Chain

  1. Inspected the website source code and found commented login credentials.

  2. Logged into the application.

  3. Identified the vulnerable YAML import feature.

  4. Confirmed unsafe PyYAML deserialization.

  5. Executed system commands and obtained a reverse shell.

  6. Enumerated the system and discovered credentials in a root process.

  7. Switched to the root user and captured both user and root flags.

Lessons Learned

  • Never expose credentials in source code or HTML comments.

  • Use yaml.safe_load() when processing untrusted YAML input.

  • Validate uploaded files and restrict accepted input.

  • Never expose passwords through process arguments.

  • Perform regular security reviews to identify misconfigurations before deployment.

Remediation

  • Remove hardcoded credentials and sensitive comments from the application.

  • Replace unsafe YAML deserialization with yaml.safe_load().

  • Validate YAML input and reject custom Python object tags.

  • Run the application with least privileges.

  • Avoid passing passwords as command-line arguments.

  • Enforce strong authentication and securely store credentials.

  • Regularly audit processes and configurations for exposed secrets.

Conclusion

The attack was successful because multiple security weaknesses were chained together, including exposed credentials, unsafe YAML deserialization, and poor credential management. Addressing these issues through secure coding practices, input validation, and proper secret management would effectively prevent this attack.
