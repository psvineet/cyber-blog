  • th above source code is revelaing much information such as the database table name, database software name, aws region and most importantly the identity pool which authorizes users to obtain temporary, limited-privilege AWS credentials.

  • and the above screenshot shows a POST request that was sent to the

    host:  cognito-identity.us-east-1.amazonaws.com for the credentials

    the server sent the credentials accessKeyid, secret key, session token etc.

  • the next post request was sent to https://dynamodb.us-east-1.amazonaws.com/ with the session token and guest id

  • then the database returned the information about the guest profile.

Understanding

By analyzing the code and the requests and reposnses I understood the app working method, the visitors browser sends a request to the server with identitypool and gets the credentials to access the records and database then the session token is used to read the table complimentary-GuestWellnessProfiles data from the dynamodb application.

So there is a vulnerability identified that the user can use the session token to read the all users data inside the complimentary-GuestWellnessProfiles.

Root Cause

The web application relied on JavaScript logic to request only the current visitor’s profile. However, the underlying IAM role (complimentary-cognito-unauth-role) granted full dynamodb:Scan permissions to unauthenticated users without any row-level restrictions.

How to Fix It

To secure DynamoDB access for unauthenticated Cognito identity pools, developers must apply Fine-Grained Access Control (FGAC) within the IAM policy using the dynamic variable

With this condition, DynamoDB ensures that guest users can only query database rows matching their assigned Cognito Identity ID, preventing unauthenticated cross-tenant data leaks.
