Pentesting Frameworks — and How to Choose the Right One

A tour of the standards and methodologies that turn penetration testing from ad-hoc poking into a repeatable, defensible engagement — and a practical way to pick one for your next job.

01Introduction

A penetration test without a framework is just hacking with extra paperwork. Frameworks exist so that two different testers, given the same scope, produce comparably thorough, comparably documented results — and so a client can hold the report up against an agreed standard rather than the tester's memory. They also protect the tester: a documented methodology, signed off before testing begins, is what separates authorised security research from a criminal offence.

Every mature framework, whatever its origin, is really answering the same four questions: what are we allowed to touch (scope), how do we approach it (methodology), how do we know we've been thorough (coverage), and how do we communicate what we found (reporting). Where they differ is emphasis — some frameworks are almost entirely about the first question, others are checklists that only address the third.

Broadly, the frameworks below fall into four buckets:

  • Methodology standards that define how to test end-to-end, phase by phase — OSSTMM, PTES, ISSAF.
  • Process guidance from standards bodies, focused on governance and repeatability — NIST SP 800-115.
  • Testing checklists scoped to a specific application layer — OWASP WSTG, OWASP MASTG.
  • Knowledge bases that catalogue adversary behaviour rather than prescribe test steps — MITRE ATT&CK.

Most real engagements blend two or three of these rather than following one to the letter. A typical setup: PTES or NIST 800-115 shapes the overall engagement lifecycle, OWASP WSTG supplies the tactical web-app checklist, and ATT&CK provides the vocabulary for describing techniques in a way a blue team will recognise.

Why this matters Frameworks aren't bureaucracy for its own sake — they're what let a pentest be repeatable, scoped, legally defensible, and comparable to the last one. A client reading a PTES-aligned report six months from now, from a different tester, should be able to tell whether coverage genuinely improved.

03OSSTMM

Open Source Security Testing Methodology Manual, maintained by ISECOM, is one of the oldest and most rigorous testing methodologies still in active use. Its defining trait is measurement: OSSTMM tries to quantify security as an actual number — the RAV (Risk Assessment Value) — rather than a list of findings with severity labels bolted on afterward.

Structure

OSSTMM organises testing into five "channels", each representing a different attack surface:

  • Human security — social engineering, awareness, trust exploitation.
  • Physical security — access controls, perimeter, physical intrusion.
  • Wireless communications — Wi-Fi, Bluetooth, RF-based attack surfaces.
  • Telecommunications — PBX, VoIP, and traditional telephony.
  • Data networks — the classic network and application layer.

The RAV score

Where OSSTMM diverges hardest from every other framework here is the RAV: a calculated figure derived from three factors — porosity (how much attack surface exists), controls (what mitigates it), and limitations (where controls fall short). The result is a single number that, in theory, lets an organisation track security posture over time the same way they'd track any other KPI.

Strengths & trade-offs Extremely rigorous, vendor-neutral terminology, genuinely comparable over time. But it's dense — the manual reads like an academic standard, not a field guide — and the RAV calculation has a learning curve that puts off testers who just want a checklist to work from.

OSSTMM tends to show up in mature security programs that already have a baseline and want to track drift, rather than in a one-off pentest for a startup's first audit.

04OWASP WSTG

The Web Security Testing Guide is the de-facto checklist for web application penetration testing, maintained by the OWASP Foundation — the same body behind the OWASP Top 10. It's organised by category, each with numbered, individually identifiable test cases.

Categories

CategoryExample checks
Information gatheringFingerprinting, entry points, web server config
Configuration & deploymentInfrastructure config, admin interfaces, HTTP methods
Identity managementAccount provisioning, role definitions, username enumeration
AuthenticationCredential transport, lockout, "remember me", MFA bypass
AuthorizationPath traversal, privilege escalation, IDOR
Session managementCookie attributes, fixation, CSRF, session timeout
Input validationSQLi, XSS, command injection, deserialization
Error handling & cryptographyStack traces, weak TLS, improper key storage
Business logicWorkflow bypass, abuse of legitimate functionality
Client-sideDOM XSS, clickjacking, WebSocket security

Each test case carries a stable ID like WSTG-ATHN-01, so findings can reference the exact check that failed — useful for both remediation tracking and comparing coverage across engagements.

Strengths & trade-offs Extremely practical and specific — each test case explains what to check, why it matters, and often how. Pairs naturally with the OWASP Top 10 as a "why this matters" companion for stakeholders. The trade-off: scope is narrow by design. It's a web app guide, not a full-network methodology, so it needs a broader framework wrapped around it for anything beyond the application layer.

05NIST SP 800-115

The U.S. National Institute of Standards and Technology's Technical Guide to Information Security Testing and Assessment is less a step-by-step checklist and more an official process definition. It draws a clear line between three related but distinct activities — review techniques (documentation, log review), target identification and analysis techniques (scanning, vulnerability analysis), and target vulnerability validation techniques (actual penetration testing) — and defines four phases for the last of these.

PhaseFocus
PlanningRules of engagement, scope agreement, authorization
DiscoveryInformation gathering and scanning to identify targets
AttackExploiting discovered vulnerabilities to gain access
ReportingDocumenting findings, risk, and recommendations concurrently with testing
Strengths & trade-offs Favoured in government, regulated, and compliance-heavy environments — it's frequently referenced directly in audit and compliance language. Strong on governance: authorization, scoping, and legal considerations get real, explicit attention, more so than most other frameworks here. The trade-off is that it's technique-agnostic — it tells you the phases and what belongs in each, not the exact commands or tools, so it's usually paired with something more tactical.

06PTES

The Penetration Testing Execution Standard is widely considered the most "practitioner-friendly" full-lifecycle methodology, put together by a working group of practicing testers rather than a standards body. It defines seven phases that map closely to how a real engagement actually runs, and — unusually for a methodology document — includes a detailed technical guide alongside the high-level standard.

PhaseFocus
Pre-engagement interactionsScoping, rules of engagement, legal sign-off, success criteria
Intelligence gatheringOSINT, recon, footprinting, target profiling
Threat modelingMapping likely attack paths to business assets and threat actors
Vulnerability analysisIdentifying exploitable weaknesses across the attack surface
ExploitationGaining access by exploiting identified weaknesses
Post-exploitationPrivilege escalation, lateral movement, persistence, measuring impact
ReportingFindings, risk ratings, and prioritised remediation guidance

Why practitioners default to it

PTES's threat-modeling phase is a genuine differentiator — it explicitly asks the tester to think about which attack paths matter to this business, rather than exhaustively testing everything with equal weight. That business-context step is often what's missing from purely checklist-driven approaches, and it's the reason PTES reports tend to read as more risk-relevant to the client than pure vulnerability lists.

Strengths & trade-offs Popular precisely because it's balanced — detailed enough to be genuinely useful during execution, general enough to fit almost any engagement type from a single web app to a full corporate network. It doesn't provide the exhaustive tool-by-tool detail ISSAF does, and it isn't as measurement-focused as OSSTMM, but for most engagements that's the right trade-off.

07ISSAF

The Information Systems Security Assessment Framework, originally published by OISSG, is one of the most exhaustive methodologies ever produced, mapping specific tools and techniques to each assessment phase across networks, applications, and physical security. At its peak it ran to several hundred pages, cataloguing individual tools alongside each testing step.

Strengths & trade-offs Extremely detailed — genuinely useful as a reference library of techniques and a checklist of "things I might have forgotten to test." The catch is that active development has stalled for years, so tool references and some technique descriptions feel dated against a fast-moving threat landscape. Best used today as a supplementary technique catalogue to cross-check coverage, rather than as a primary methodology to follow start to finish.

08MITRE ATT&CK

Not a testing methodology in the traditional sense — ATT&CK (Adversarial Tactics, Techniques, and Common Knowledge) is a knowledge base of real-world adversary behaviour, built and continuously updated from observed threat actor activity rather than theoretical coverage.

Tactics & techniques

ATT&CK is organised as a matrix: tactics across the top (the adversary's objective at each stage — initial access, execution, persistence, privilege escalation, defense evasion, credential access, discovery, lateral movement, collection, command and control, exfiltration, impact) and techniques underneath each one (the specific ways that objective gets achieved), each with a stable ID like T1566 for phishing.

Strengths & trade-offs Widely used to structure red team and adversary emulation engagements rather than checklist-style pentests — the point isn't "did we test everything" but "did we realistically emulate what a specific threat actor would do." It gives a shared vocabulary between red teams, blue teams, and threat intel, which makes post-engagement conversations far more productive. It doesn't tell you how to scope an engagement or write a report — it pairs with PTES, OSSTMM, or NIST 800-115 as the "what techniques to actually use" layer inside a broader methodology.

09Other Notable Frameworks

OWASP MASTG

Mobile Application Security Testing Guide — the WSTG's counterpart for iOS and Android apps, covering platform-specific storage, IPC, and binary protection checks.

PCI DSS Penetration Testing Guidance

Compliance-driven requirements for testing cardholder data environments, including explicit segmentation testing requirements.

CREST

Accreditation-based standard used heavily in the UK/APAC, focused on tester certification and engagement quality assurance rather than a testing methodology itself.

OWISAM

Open Wireless Security Assessment Methodology — a niche, wireless-focused counterpart to OSSTMM's wireless channel.

OSSTMM's Open Testing Guide (OTG)

A lighter-weight companion checklist derived from OSSTMM concepts, useful when the full RAV process is overkill.

NIST CSF

The Cybersecurity Framework proper — broader than a pentest methodology, but frequently used to map findings back to organisational risk categories.

10Legal & Rules of Engagement

Every framework above assumes one thing that's easy to skip past: written, signed authorization before any testing begins. This is not optional paperwork — testing systems without explicit permission is, in most jurisdictions, indistinguishable from unauthorised computer access under the law, regardless of intent.

  • Get-out-of-jail letter: a signed authorization document naming the tester, the scope, the testing window, and the systems covered — carried during the engagement in case activity triggers an incident response.
  • Explicit scope boundaries: IP ranges, domains, and systems that are in scope — and just as importantly, what's explicitly out of scope (third-party integrations, production payment systems, etc.).
  • Rules of engagement (RoE): permitted techniques (is social engineering in scope? DoS testing?), testing windows, and an emergency contact who can pause the engagement.
  • Data handling terms: what happens to any sensitive data accessed during testing — retention, destruction, and disclosure obligations.

NIST SP 800-115 and PTES both dedicate explicit sections to this; OSSTMM's "Rules of Engagement" concept formalises it further with defined trust levels. Whichever framework anchors the engagement, this step happens first, in writing, before a single scan is run.

11Reporting

A framework's methodology only matters if the output is something a client can act on. Across PTES, NIST 800-115, and OSSTMM, the reporting expectations converge on a similar shape, even if the terminology differs:

  • Executive summary — business-risk framing for non-technical stakeholders: what was found, how bad is it, what should happen next.
  • Scope & methodology recap — what was tested, what wasn't, and which framework or standard was followed, so the report is auditable against it.
  • Findings, ranked by risk — not just severity, but exploitability and business impact combined (a critical CVE on an isolated dev box ranks differently than a medium finding on a production auth server).
  • Reproduction steps & evidence — enough detail that a developer can reproduce and verify the fix, without becoming a how-to guide if the report ever leaks.
  • Remediation guidance — specific, prioritised, and realistic given the client's stack — not a generic "patch your systems."
A report is the deliverable Clients rarely remember the exploitation chain in detail six months later — they remember whether the report told them clearly what to fix first. Framework choice shapes methodology, but reporting quality is what actually gets judged.

12Choosing a Framework

In practice, the choice usually comes down to engagement type and audience, not personal preference:

  • Web application only? Lead with OWASP WSTG (and MASTG for the mobile client, if there is one).
  • Full network / infrastructure engagement? PTES gives the best balance of structure and flexibility for most teams.
  • Regulated or government client? Anchor the process to NIST SP 800-115 for the paper trail auditors expect.
  • Red team / adversary emulation? Structure the operation around MITRE ATT&CK tactics and techniques rather than a checklist.
  • Need a quantifiable security score to track over time? OSSTMM's RAV is the only framework here built explicitly for that.
  • Need exhaustive technique coverage as a sanity check? Cross-reference against ISSAF, even if it isn't the primary methodology.

Most senior testers don't pick one and discard the rest — they use PTES or NIST 800-115 for the overall engagement shape and legal scaffolding, OWASP WSTG or MASTG as the tactical checklist for the layer being tested, and ATT&CK to describe techniques in a report a blue team will actually recognise. The framework is scaffolding, not a straitjacket.

Takeaway The "right" framework is the one that matches your scope, your client's compliance needs, and the report your audience already speaks the language of. When in doubt, layer them: governance from NIST or PTES, tactics from WSTG or ATT&CK, and — if the client wants a trackable score — measurement from OSSTMM.
